Benchmarks · choosing a model

Which model should run your tests?

blastproof brings no model of its own: you pick one, and its verdicts decide whether a pull request can merge. So we measure how often each model's verdict is wrong, on an app with bugs planted on purpose, and publish what we find.

The short answer

Leave the default.

Each provider's default model was chosen on the benchmark below. A config that sets no llm.model gets it.

provider: anthropic claude-haiku-4.5

No wrong verdict in 90 runs, and remeasured on every release.

provider: openai gpt-6-luna

No wrong verdict in 90 runs, and every bug caught at the step that checks it.

provider: ollama gpt-oss:20b

The fewest false FAILs of the open-weight models measured, for runs that never leave your machine. Expect a few more red builds.

How it is measured

Two ways a verdict is wrong.

The benchmark runs the demo app's test suite five times on the app as it is, and once per sample on each of ten mutants: copies of the app with one bug seeded where a test checks.

False FAIL

A test fails on the correct app. A merge gate that is red for no reason gets switched off, and then it catches nothing. This is the number we decide on first.

False PASS

A test passes on an app with the very bug it exists to catch. The bug reaches production with a green check next to it.

Literal and subtle bugs

A literal mutant changes the value a step quotes. A subtle one reproduces a wrong verdict this project has already had: the right number in the wrong place, a success message with nothing saved behind it.

Bounds, not promises

Zero errors in 40 runs means "below about 9%" at 95% confidence, not "never". The demo app is small and well labelled, so a real application will do worse.

On false PASS, no model can be told apart from another at this sample size: every 95% upper bound falls between 11% and 17%. False FAIL is where they differ, and it is what decided the defaults. gpt-oss-20b was measured through OpenRouter, not Ollama: the same weights, a different runtime.

When the default is not for you

Pick by what you can't afford.

  • Nothing may leave the machine

    gpt-oss:20b on Ollama. Its one false PASS accepted order #BP-1002 for the #BP-1001 the step asked about. It needs about 14 GB: ollama pull gpt-oss:20b.

  • A missed bug costs more than a red build

    qwen3.6-35b-a3b caught the most bugs at the right step among open-weight models and never failed to sign in. It also failed 11 of 40 tests on the correct app, and needs more memory.

  • You are on an old default

    gpt-4o-mini and qwen2.5 failed almost every test on the correct app. If your config pins one of them, remove llm.model to get the measured default.

  • Open-weight models through a gateway

    Some gateway providers ignore the JSON schema every call sends. Route around them with llm.extra_body; the configuration guide shows how.

What a run spends

Calls and tokens, read off the run.

Every run ends with a Spent: line. Cost grows with the number of steps, how dense your pages are and how often the agent retries, so run your suite once and read it. Two measured examples:

This repository's suite · claude-haiku-4.5
115ktokens

7 tests and 31 steps on the demo shop, signed in: about 82 model calls, 156 s serially or 68 s at --concurrency 4.

A real budgeting app · claude-haiku-5.5
1.8Mtokens

21 tests on pages of up to a thousand snapshot lines: about 320 model calls, 2026-10-14. Three times the tests of the demo suite, sixteen times the tokens: dense pages cost more than test count.

Measure your own

Any model, one command.

The benchmark is part of the repository, not a claim about it. Through any OpenAI-compatible gateway:

reliability benchmarkabout 1 hour per model
# from a clone of hamc/blastproof
npm install && npm run build
export BLASTPROOF_LLM_PROVIDER=openai
export BLASTPROOF_LLM_BASE_URL=https://openrouter.ai/api/v1
export BLASTPROOF_LLM_API_KEY_ENV=OPENROUTER_API_KEY
EVAL_MODELS=openai/gpt-oss-20b npm run eval:reliability

Models that cannot take every role are measured on the one they could take. Jev, a decision model that writes no text, was measured as the judge. The method and every past result live in the configuration guide.
