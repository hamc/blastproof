# AGENTS.md — blastproof

> Central context for AI agents and contributors. Read this before touching code.

## Mission

**blastproof** is an open-source AI testing agent for pull requests. Given a code diff, it maps the blast radius, generates plain-English E2E tests, executes them on a real browser through an agentic self-healing loop, and reports a score that can gate merges. 100% local, BYOK (bring your own LLM key). MIT licensed.

Pipeline: `git diff → impact mapping → test generation → agentic execution → report + score`

## Capabilities and scope

| Capability | blastproof MVP |
| --- | --- |
| PR diff analysis | ✅ `blastproof run --impacted --base main`, `blastproof plan --base main` |
| Blast radius mapping | ✅ deterministic (config `routes:` globs). Catches *unclassified* files, not *misclassified* ones — import-graph impact is the open gap |
| Plain-English YAML tests | ✅ `.blastproof/tests/*.yaml` (summary, steps, priority, tags, routes) — handwritten or generated by `plan` |
| Scriptless agentic execution | ✅ own loop: Playwright `ariaSnapshot()` + LLM structured output |
| Self-healing (no static selectors) | ✅ elements re-resolved by role/name every step |
| Score with merge threshold | ✅ priority-weighted (P0=3, P1=2, P2=1), `--min-score` gate |
| JUnit/HTML reports | ✅ JUnit XML and a self-contained HTML report with embedded screenshots |
| CI integration | ✅ published to npm and a composite GitHub Action; PR comments still post-MVP |
| Authentication | ✅ sign in once per run — login journey, captured session, or static headers/cookies |
| Unclassified-change gate | ✅ `ignore:` globs + `--fail-on-unmapped` for files whose blast radius nobody declared |
| Run budget & deadline | ✅ optional `budget:` (calls/tokens/duration) + matching flags; exhaustion stops the run as **incomplete**, never as a failed test — exits 1 regardless of `--min-score` |
| SaaS backend, credits, dashboards | ❌ never — local-first BYOK |
| VS Code extension, Flutter, session replay | ❌ post-MVP |

## Tech stack

- **Runtime**: Node.js ≥ 20.19 (see `engines` in `package.json`; use any version manager you like), TypeScript strict, ESM (`"type": "module"`, NodeNext resolution)
- **Browser**: Playwright (Chromium only in MVP) — snapshots via `page.locator('body').ariaSnapshot()`
- **LLM**: Vercel AI SDK (`generateObject` + Zod schemas) — providers: Anthropic, OpenAI, Ollama (OpenAI-compatible)
- **CLI**: commander · **Config/tests**: `yaml` · **Git**: simple-git · **Build**: tsup · **Tests**: vitest
- **SDD**: OpenSpec (`openspec/` + slash commands `/opsx:*`)
- **Distribution**: published to npm as `blastproof`; the consumable composite action is `action.yml` at the repository root; the agent skill is `skills/blastproof/`, installed straight from this repository by `skills add` and never shipped in the npm tarball (`files` is `["dist"]`)

## Target architecture (`src/`)

```
src/
  cli.ts            # entry: init | run | plan | test
  config.ts         # loads .blastproof/config.yaml (zod-validated)
  diff.ts           # git diff base...head → changed files + context
  impact.ts         # diff + route hints → affected journeys/URLs
  planner.ts        # generates YAML tests for affected-but-uncovered routes
  auth.ts           # sign in once per run; all strategies yield one browser session
  commands/
    init.ts         # scaffolds .blastproof/ (idempotent, never overwrites)
    run.ts          # discovery → filters/impact → execution → score → reports
    plan.ts         # drafts tests for affected-but-uncovered routes
    test.ts         # the one-shot pipeline: run --impacted, then plan
  runner/
    executor.ts     # agentic per-step loop (retry budget, self-heal)
    snapshot.ts     # ariaSnapshot capture + trimming
    actions.ts      # navigate/click/fill/press/select/assert via getByRole
    selection.ts    # tag/priority/query filters + impacted selection
    testfile.ts     # YAML test discovery and validation
    env.ts          # {{env.*}} substitution + secret masking
    budget.ts       # run-wide call/token/deadline budget + dry-run ceiling + spend
    recovery.ts     # per-step record; refuses a repeated commit (contained-recovery)
    pool.ts         # bounded runWithConcurrency, results in input order (tests-in-parallel)
    browser.ts      # browser launch, with a failure explained without the Chrome argv
  llm/
    provider.ts     # AI SDK provider factory (anthropic|openai|ollama)
    prompts.ts      # system/user prompts for plan + execute + assert
    brain.ts        # structured decisions: executor loop + planner
    schemas.ts      # zod schemas for every model response
  report/
    score.ts        # priority-weighted score + --min-score gate
    junit.ts        # JUnit XML (CI-compatible)
    html.ts         # self-contained HTML report with embedded screenshots
```

### Conventions

- **Test files** (the product's, not ours): `.blastproof/tests/**/*.yaml` — fields `summary` (required), `steps` (required, plain English), `priority` (P0–P2), `tags`, `routes`, optional `setup`, `auth` (default true; a login test must set `false`), `{{env.VAR}}` placeholders for secrets
- **Config**: `.blastproof/config.yaml` — `base_url`, `llm.{provider,model,api_key_env}`, `browser`, `routes` (glob→URLs impact hints), `ignore`, `allowed_origins`, `max_retries_per_step`, `budget`, `concurrency` (default 1, opt-in — see below), optional `auth` recipe (one of `steps` | `storage_state` | `headers`/`cookies`, plus optional `verify` and `cache`). Overridable from the environment via `BLASTPROOF_*`
- No static selectors anywhere in generated tests or runner state — resolution is always live via accessibility tree
- **The OpenSpec skills carry `metadata.internal: true`, and a regeneration will drop it.** `skills add <owner>/<repo>` walks `skills/` *and* the agent directories, so before this marker the command the README publishes installed this repository's six `openspec-*` skills into other people's projects alongside the one they asked for — six skills instructing their agent to run an `openspec` CLI they do not have. The marker hides them from that discovery and changes nothing for us. They are generated files (`generatedBy` in their front matter), so whoever regenerates them must put it back; `tests/skill-manifest.test.ts` fails when it is missing
- **`skills/` is user-facing content, held to the same drift guard as `action.yml`.** `skills/blastproof/**` is installed into other people's projects by `skills add` and read by their coding agent, so a stale flag name there is not a confusing sentence someone reports — it is confident wrong instructions a machine follows without complaint. `tests/skill-manifest.test.ts` reads every fenced block and inline span — never prose — and fails when the skill names a command the CLI does not have, uses a flag the command it invokes does not declare, documents a flag under the wrong command in `cli.md`, or lets its quoted authoring rules stop being set-equal to `plannerSystemPrompt()`'s, minus one named planner-only rule. The rules are **copied whole rather than restated**, because a paraphrase cannot be compared mechanically at all, and compared by set equality rather than containment, because containment lets a rule be truncated to a prefix and still pass. The first version of this guard read only inline spans, so every command in a fenced block — which is every command an agent actually runs — went unchecked while the test stayed green; assume the same class of hole until a mutation proves otherwise. This bounds the duplication #45 describes without resolving it — collapsing the copies to one generated source is the real fix and needs its own proposal
- `npm run typecheck` covers `tests/` as well as `src/` (`tsconfig.typecheck.json`). Vitest transpiles with esbuild, which strips type annotations without checking them, so a test asserting on a field that does not exist reads `undefined` — and the negative forms (`toBeUndefined`, `not.toBe`) pass silently rather than failing. `tsconfig.json` stays `src`-only because it carries the build's `rootDir`
- Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:` …), one-line subject
- Secrets never enter a prompt: `{{env.*}}` placeholders survive to action time and are substituted immediately before use. Values are also masked in the reports' **text**. The mask compares by normalization, never by byte equality — the registered value case-insensitively, with runs of whitespace matched loosely, the same rule `agentic-execution` uses to decide whether a typed value came from the page. It is deliberately the whole rule: a value the application re-encodes or hashes cannot be recognised, and enumerating transforms would imply a completeness no mask has. Where a redaction is found only by that widening, the run says so once, naming the variable and never the value (#109). A redaction is a label naming its variable, `[redacted NAME]`, never one shared token: with a single `***`, every secret looked like every other after masking, and a step verifying one passed against a page showing another (#87). A typed value containing a label is refused, because the label is on the masked page the model read and the source check alone would admit it. Masking cannot reach pixels: a failure screenshot shows whatever was on screen, so the HTML report withholds screenshots from any run whose mask holds a value and links to the file instead (#110). See `openspec/changes/archive/2026-09-19-withhold-a-screenshot-that-saw-a-secret`
- The agent may not navigate outside `base_url`'s origin plus any declared `allowed_origins`. Enforced in `actions.ts`, not by prompt wording.
- Never log secrets; `{{env.*}}` values are masked in report text, and a screenshot from a run that held one is never embedded in a report. A captured auth session is a live credential: git-ignored, never printed, never embedded in a report
- A run's budget (calls/tokens/deadline, optional `budget:` in config) is a run-wide guarantee enforced at the single choke point every model call passes through — `createBrain`/`createPlanner` in `llm/brain.ts` — the same shape and the same reason as the secrets mask above: a guarantee implemented at a call site instead of over the whole scope is this codebase's recurring defect (it produced the secret leaks, and it produced #15). Exhausting it ends the run as **incomplete**, never as a failed test — see `openspec/changes/archive/run-budget-and-deadline` (once archived) for the reasoning. A model provider that gives no response stops the run on the same path, for the same reason (#125). It covers an HTTP error status or no answer at all, after the SDK's own retries. The stop is converted once, in `countedGenerate`, from the error's type and status, never its message. Every site that ends a run tests `RunStoppedError`, the base of both causes, never one of them, and `tests/budget.test.ts` fails on an `instanceof BudgetExhaustedError` in `src/`. See `openspec/changes/archive/2026-10-04-stop-the-run-when-the-provider-refuses`
- **A verdict must describe the page the action produced.** The executor waits for the page to settle before every snapshot, and a failed judgment re-observes the same expectation against a freshly settled page before control returns to the model. Both exist because a verdict reached on a page mid-navigation is wrong in the worst direction — it failed a step that had succeeded, on a real application, twice. Note the measured constraint before changing this: only `networkidle` narrows that window (`domcontentloaded` and `load` return in about a millisecond on the page being replaced), and it therefore has a short budget of its own rather than `browser.timeout_ms`, because it is also the state most likely never to arrive. See `openspec/changes/archive/trustworthy-verdicts` (once archived)
- Every error message at the prerequisite boundary (a missing browser, an unreachable model provider, a stopped app, a missing API key) is held to the standard the missing-API-key message already sets: name the variable or component, name the provider or command, and give a copy-pasteable remedy. `MissingApiKeyError` (`llm/provider.ts`) is that standard; `preflight.ts` and `runner/browser.ts` exist because Playwright's raw launch exception was proportionally worse for being the one unhandled path in an otherwise exemplary set — see `openspec/changes/archive/onboarding-preflight` (once archived) for the reasoning
- **Concurrency is opted into, and the default is 1.** Other test runners default to parallel because their tests are isolated by construction; ours are journeys driven against one running application, so two tests that write to it can see each other's data. This repository's own notes test is the shape — it writes shared server state *and* asserts on a global count, so it cannot run beside itself. A tool that gates merges must not start producing failures from its own scheduler on upgrade. Raising the default is a decision for whoever knows the suite, never ours. See `openspec/changes/archive/tests-in-parallel` for the reasoning
- **A judgment decides the step, not a claim about the page.** `judge()` takes the step alongside the model's expectation; the expectation is the claim offered in support of the step, not a substitute question of its own — a claim that is true of the snapshot and does not establish what the step describes must not pass it. This closed a wrong PASS confirmed against a real application's database (`GET /api/v1/projects` showed a project absent while the tool reported `Score: 100`, twice, via two different malfunctions): a true-but-irrelevant claim closing a step whose real assertion had already failed, and a value sitting in an unsubmitted dialog's textbox being accepted as a committed outcome. Anchoring on the step rather than making a failed judgment permanently sticky is deliberate: the blunt fix would also have discarded the re-observation `trustworthy-verdicts` added for a page that had not yet settled, which is working and must survive. See `openspec/changes/archive/judge-the-step` (once archived) for the reasoning
- **A verification step only looks.** A step whose first word is `verify`, `check`, `confirm`, `ensure`, `assert`, `expect` or `validate` (or `make sure`, `see that`) may not click or press Enter, and closes only on a passing judgment, never on `done`. On a page that did not satisfy it, both reference models clicked "Add to cart" to produce the message the step checked, and the step passed (#139). That is the one runtime guarantee here that reads the step's wording, and it is English only, against `close-a-step-on-what-was-done`'s choice of no semantics (#72). It is justified by the direction of its errors: a step taken for a check that needed a click fails visibly on the refusal, and a check it misses runs as before, so neither creates a false PASS. See `openspec/changes/archive/2026-10-05-a-verification-step-only-looks`
- **A change to the judge replays the judge corpus before it merges.** `evals/judge/` holds judge inputs with known correct verdicts from every verdict incident (#31, #35, #87, #112, #120, #121, #141, #147); `npm run eval:judge` runs them through the real `judge()`. Nine changes to the verdict were each verified against their own reproduction and a dogfood suite that contained none of these cases, so nothing would have shown a later one reopening an earlier one; #87's fix missed the placeholder form exactly that way. The judge reads the step, the claim and the record with every `{{env.NAME}}` rewritten as `[redacted NAME]`, the vocabulary the page is in, and its schema asks whether the snapshot shows the **step's** outcome, reason before verdict (#120). Neither held alone against a live run: after the model's verdict, `judge()` also fails a PASS on a step naming `[redacted X]` when X's label is in neither the snapshot nor the step's record while another label is on the page — a check on tokens the mask writes, not on prose, because the model still called two different labels a match. A variable used in an action of an earlier step of the same test also counts as accounted for: since #121 a "log in with … and verify" step whose login already happened names a password it never typed, and the check failed it (#141). A place the step names is part of its outcome. On a page with `#BP-1002` in the confirmation and `#BP-1001` in a paragraph about a previous order, a claim calling that paragraph "the confirmation message" got the step passed on Haiku (#147). The fix is again two pieces of prose that only work together: a prompt paragraph that moved the reason, and a sentence in `pass` that moved the verdict. A broader sentence ("a reason that places the value elsewhere is a reason for false") broke two #121 cases. Measure every word added there. Checking only the labels in the judgment's `outcome` was rejected because Haiku's rewrite swapped the expected label for the page's in 3 of 99 judgments — the confusion the check exists for. A new verdict incident adds its case to the corpus as part of its fix. The replay runs on two models, `EVAL_MODELS=anthropic/claude-haiku-4.5,openai/gpt-6-luna`: Haiku because it is the default an unconfigured user's verdicts come from, Luna because it is another family. #121's fix was three pieces of prose that worked only together, measured on Haiku alone, and #129 turned out to be Haiku's limit rather than the judge's: Luna judges its cases right. A regression on either model fails the replay, and a known failure counts as fixed only on both. See `openspec/changes/archive/2026-10-03-ask-the-judge-about-the-step` and `openspec/changes/archive/2026-10-05-replay-the-judge-corpus-on-two-models`
- **How often a verdict is wrong is measured, not assumed.** `npm run eval:reliability` (`evals/reliability/`) runs the dogfood suite on the demo app as it is (false FAIL) and each targeted test on **mutants**, copies with one seeded bug (false PASS), and reports the rates with a 95% upper bound per model. Every wrong verdict before it (#87 through #141) was found by chance or an adversarial pass. A mutant breaks only what its target's steps check, or it measures coverage instead of verdicts. Its edits must apply exactly once, and `tests/reliability.test.ts` checks this against the demo app, so editing the app can fail CI until the mutant's text is updated. A literal mutant changes the value a step quotes. Both reference models caught all of those in the pilot, so a benchmark of literal mutants alone would publish a flattering zero. Subtle mutants reproduce the shape of a past wrong verdict and name it. See `openspec/changes/archive/2026-10-07-measure-verdict-reliability`
- **A step is judged on the state it asks for, not on its action.** The judgment states the step's outcome first, as a sentence with the action taken out, and then decides that sentence. Asked about "dismiss the dialog and verify it is gone" on a page where an earlier step had already dismissed it, the judge failed it for want of a dismissal (#121). The verb was read as a requirement, whatever the claim said. The means is therefore not checked: a snapshot records a state, not the path to it, and a step whose means matters names what the means leaves on the page. The fix is three pieces of prose, the `outcome` field, two sentences in `pass`'s description and one paragraph in the judge's prompt, and leaving out any one left a captured input wrong. Nothing but the corpus holds them in place. See `openspec/changes/archive/2026-10-04-judge-the-outcome-not-the-means`

## Where the work comes from

**Start here when picking up this project.** Two systems, with a deliberate division:

- **GitHub Issues** are the inbox: a problem someone observed, not yet a decision. `gh issue list` is the backlog, and every known gap lives there rather than in someone's head.
- **OpenSpec changes** are committed work: an issue graduates into a proposal with a design, and the design records the alternatives that were rejected and why.

The public [roadmap](https://github.com/users/hamc/projects/2) is a view over issues, never a third place for work: every card is an issue, placed by `Horizon` (Now / Next / Later, never dates) and `Theme` (Trust, PR-first, Cost & speed, Reach). An idea worth showing there is filed as an issue first.

An issue may sit open indefinitely; a change should not. If you are looking for what to do next, read the issues. If you are looking for why something is the way it is, read `openspec/changes/archive/` — that is where the reasoning lives, not in the commit that shipped it.

## Spec-driven development workflow (REQUIRED)

This repo uses [OpenSpec](https://github.com/Fission-AI/OpenSpec). **No code change without an approved change proposal.**

1. **Propose** — `/opsx:propose "<what>"` (or `openspec new change <kebab-name>` + author artifacts). Creates `openspec/changes/<name>/` with `proposal.md`, `design.md`, `tasks.md` and spec deltas under `specs/`
2. **Review** — human reviews the proposal before implementation
3. **Apply** — `/opsx:apply` implements tasks from `tasks.md`, checking them off
4. **Archive** — `/opsx:archive` merges deltas into `openspec/specs/` (living source of truth), **in the same pull request as the implementation, as its own commit** — the reasoning is in `CONTRIBUTING.md` and lives there only, because a rule written twice is a rule that drifts

Rules:

- Keep proposals small (one milestone/feature per change)
- Specs use `SHALL` requirements with `WHEN/THEN` scenarios
- Update `tasks.md` checkboxes as you complete work
- If implementation diverges from design, update the change artifacts first

## Multi-agent workflow (optional, opencode)

Subagents in `.opencode/agents/` mirror a small delivery team with strict separation of duties (file permissions enforce it):

- `dev` — implements tasks from an approved OpenSpec change (code + unit tests). Never touches `openspec/` artifacts, never commits.
- `qa` — verifies: build/typecheck/test + E2E against `examples/demo-app/`; owns `DEFECTS.md` and is the only role that closes defects. Never edits product code.
- `sentinel` — read-only reviewer: secret leaks/masking, static selectors, unjustified dependencies, spec and convention drift. Never edits anything.

Delegate via the Task tool. The primary agent (or the human) orchestrates: dispatches tasks, triages defects, and checks off `tasks.md` boxes only after `qa` verifies.

The same three agents are also ported to **Claude Code** (`.claude/agents/`), with cost-tiered models: orchestrator/main agent runs Opus (`.claude/settings.json`), `dev` and `qa` run Sonnet, `sentinel` runs Haiku.
