## DEF-001 — Dry-run ceiling (`estimateMaxModelCalls`) can undershoot the true worst-case call count
- Status: CLOSED
- Severity: HIGH (breaks a requirement)
- Found by: qa
- Steps: numbered, from a clean state, with exact commands
  1. From the repository root, note two constants that determine one test step's real worst-case model-call count in `src/runner/executor.ts`:
     - `DEFAULT_MAX_ITERATIONS_PER_STEP = 15` (`N`), hardcoded, not configurable anywhere (no CLI flag, no config field).
     - `config.max_retries_per_step` (`R`), a user-configurable value in `.blastproof/config.yaml` (`z.number().int().min(1)`, default 3, **no upper bound**, and not required to relate to `N` in any way).
  2. In `src/runner/executor.ts`'s per-step loop (`executeTest`), a malformed/invalid model response (`brain.nextAction` throwing) increments `failedAttempts` (the retry budget, capped at `R`) but does **not** increment `iterations` (the cap checked against `N`). A failing `assert` judgment increments both `iterations` and `failedAttempts` and costs two real model calls (`nextAction` + `judge`). This means the real worst-case number of model calls for one step is `N + R`, not `2N` as `estimateMaxModelCalls` (`src/runner/budget.ts`) computes (`totalSteps * maxIterationsPerStep * 2`).
  3. `2N > N + R` only holds while `R <= N` (true only for the *default* `max_retries_per_step: 3` vs. the fixed `N=15`). Setting `max_retries_per_step` above 15 in config — a perfectly legal value per the zod schema — makes `N + R > 2N`, i.e. the real ceiling exceeds the reported one.
  4. Reproduced empirically (script run outside the repo, against unmodified `src/runner/executor.ts` and `src/runner/budget.ts`, no product code edited): a single-step test executed via `executeTest` with `maxIterationsPerStep = 15` and `maxRetries = 20`, driven by a scripted brain that (a) returns malformed output `R-1=19` times, (b) then returns `N-1=14` plain successful actions, (c) then one `assert` action whose judgment always fails (the step's final, terminating call) — produced **35** real model calls (34 `nextAction` + 1 `judge`), while `estimateMaxModelCalls([{steps:['single step']}], 15)` reports a ceiling of **30**.
- Expected: per spec `run-budget`, "Scenario: Estimate is an upper bound, not a prediction" — the dry-run number must be "the ceiling the selection cannot exceed" (design D5). A real run must never spend more model calls than the number `--dry-run` reported.
- Actual: with a legal (if unusual) `max_retries_per_step` value greater than the fixed 15-iteration cap, a real run can spend more model calls than the reported ceiling — the estimate undershoots, which design D5 and the task itself single out as strictly worse than reporting no ceiling at all ("an estimate that undershoots is worse than none").
- Evidence: empirical repro script executed via `npx tsx` against the unmodified `src/runner/executor.ts` / `src/runner/budget.ts` (script and its output not persisted in the repo, per QA's read-only scope; output captured below):
  ```
  N (maxIterationsPerStep, fixed default) = 15
  R (config.max_retries_per_step, user-configurable, e.g. 20) = 20
  step status: failed / reason: forced failure to consume the last retry unit
  nextAction calls: 34
  judge calls: 1
  TOTAL real model calls made: 35
  estimateMaxModelCalls() ceiling for this 1-step test: 30
  DEFECT CONFIRMED: real calls (35) EXCEED the reported ceiling (30)
  ```
  Formula for anyone who wants to reproduce without the script: true per-step worst case is `maxIterationsPerStep + max_retries_per_step` (not `maxIterationsPerStep * 2`); the two diverge, in the estimate's favor being wrong, exactly when `max_retries_per_step > maxIterationsPerStep` (i.e. > 15, since `maxIterationsPerStep` has no config/flag and is fixed at `DEFAULT_MAX_ITERATIONS_PER_STEP`).

## DEF-002 — Preflight's fixed 5s reachability timeout produces a false negative against a slow-but-working `base_url` or provider
- Status: CLOSED
- Severity: HIGH (breaks a requirement)
- Found by: qa
- Steps: numbered, from a clean state, with exact commands
  1. From the repository root, note `src/preflight.ts:6`: `const REACHABILITY_TIMEOUT_MS = 5000;` — hardcoded, not read from config, not overridable by any CLI flag or env var, and used for both the `base_url` probe and the model-provider probe (`probe()`, used by both `checkModel` and `checkBaseUrl`).
  2. Started a plain Node `http` server (outside the repo, no product code edited) that accepts the connection immediately but delays writing its response by 6 seconds — modelling an ordinary, working dev server on a slow first request (e.g. a framework compiling a route on demand, a cold-starting container, a loaded CI runner), not an actually-down one.
  3. Called `runPreflight({ browser: false, model: false, baseUrl: true }, { base_url: 'http://localhost:58081', ... })` (unmodified `src/preflight.ts`, via `npx tsx`) against that server.
  4. Repeated against a slow *model provider* endpoint the same way (`llm.base_url` pointed at a TCP listener that accepts the connection but never writes a response), calling `runPreflight({ browser: false, model: true, baseUrl: false }, ...)`.
- Expected: per design D6, "a false failure at preflight blocks a run that would have worked — strictly worse than the dump it replaces," and the risk section explicitly names this as "the worst outcome available here." A server that is genuinely up and would have answered — just slowly — must not be reported as down at 5 seconds, especially with no way to raise the timeout for a known-slow setup.
- Actual: both probes abort at exactly the hardcoded timeout and report the endpoint as unreachable/not-responding, even though it was live and about to answer:
  ```
  elapsed ms: 5010
  { "ok": false, "failures": [
    "The application at http://localhost:58081 is not responding (This operation was aborted). Start it, or point --url / base_url in .blastproof/config.yaml at the right address."
  ]}
  ```
  and, for the model check, the identical timing/shape:
  ```
  elapsed ms: 5004
  { "ok": false, "failures": [
    "Cannot reach the anthropic provider at http://localhost:58080 (This operation was aborted). Check your network connection or llm.base_url in .blastproof/config.yaml."
  ]}
  ```
  The error message itself ("This operation was aborted") also gives no indication that a timeout — rather than an actual connection failure — is what happened, so the message misleads about the cause as well as the verdict. This is a real preflight run against real TCP servers and the unmodified `src/preflight.ts`/`src/runner/browser.ts`, not a mock.
  A 5-second budget for "did the app's very first response arrive" is tight enough to trip on ordinary conditions this project's own examples can hit (a dev server compiling a route on first request, a container still warming up, a loaded CI runner) — all cases where the underlying `run` (whose browser navigation timeout is `config.browser.timeout_ms`, default 30000ms, six times as generous) would have succeeded had preflight not stood in front of it. There is no flag, env var, or config field to raise this timeout for a setup known to be slow but valid; the change's own "Open Questions" anticipates exactly this shape of problem ("Should preflight be skippable with a flag ... ? Leaning yes if a false negative is ever reported") but no such escape hatch exists yet.
- Evidence: reproduced with `npx tsx` against unmodified `src/preflight.ts`, using a throwaway Node `http`/`net` server outside the repo (script and server not persisted, per QA's read-only scope). Raw output captured verbatim above. `grep -n "REACHABILITY_TIMEOUT_MS" src/preflight.ts` confirms the single hardcoded constant with no override path.

## DEF-005 — Anchoring the judge to the step introduced two regressions that only a real model could surface
- Status: CLOSED
- Severity: HIGH (both produced wrong verdicts on working journeys)
- Found by: orchestrator, during `judge-the-step` group 5 verification against live Vikunja
- Context: `judge-the-step` gave the judge the step as the question, fixing a confirmed wrong PASS. Both regressions below passed a green unit suite and were caught only by running a real model against a real application.
- Regression 1 — the synthetic auth step was a transcript of actions. `auth.ts` built the step as `complete the login journey: navigate to /login; fill ...; submit ...`. On a login that genuinely succeeded, the judge anchored on those actions and reported `Authentication could not be verified: the snapshot shows the user is already signed in ... not at the /login page where the step begins`, aborting the run with exit 2. Intermittent: the same code and config authenticated correctly minutes earlier. Fixed by passing `auth.verify` as both the step and the expectation — here they genuinely are the same claim, and `auth.verify` is already author-written and outcome-shaped.
- Regression 2 — an action-shaped step became unjudgeable exactly when it succeeded. `submit the login form` failed with *"the user is already logged in ... not a login form, so the step outcome of submitting a login form cannot be established"*. Succeeding navigates away from the control the step names, so the judge could not tell "the action worked" from "the thing named is missing". Also unstable: `submit the support form` in our own demo suite passed in the same session, the judge reasoning that the confirmation page *was* the outcome. Fixed with a prompt clause: a step naming an action is satisfied by evidence the action took effect, not by the continued presence of the control it names — narrowed so a real negative signal (an error, a validation warning, the unchanged pre-action page) still fails.
- Why the unit suite could not catch either, in the dev's words: *"my fakes ARE the specification of judge behaviour, so a fake that gets the reasoning right proves the wiring can carry a correct answer, never that the model will find it."* A deterministic double eliminates precisely the ambiguity that produces this class of defect.
- Structural lever identified and deliberately NOT taken **at the time**: the judge never receives `lastResult` (e.g. `ok: clicked role=button name="Login"`), although `nextAction` does. It therefore infers whether an action happened from the step's grammar and the page state, when the executor already holds the fact. Recorded as the first thing to try if a third regression in this family appears — before adding a fourth prompt clause. **Taken on 2026-07-31; see the History entry below.**
- Verified: the wider Vikunja suite after both fixes gives 5 passed / 2 failed, every verdict checked against the application's database. The negative control still fails correctly. The one unexpected failure is #28 (repeated side effects), not a judge defect — four duplicate tasks the tool itself created, correctly reported as still visible.
- Observed interaction worth its own attention: a stricter judge amplifies #28. More failed assertions means more recovery attempts, and recovery can write. The same test produced one record before this change and five after.
- History: 2026-07-30 found, fixed and verified within `judge-the-step`, before merge.
- History: 2026-07-31, **the structural lever was taken** (0.10.0, change `judge-sees-the-record`, #35). The third regression of this family arrived exactly as anticipated — a step naming a path failed when the server redirected, because a successful navigation to a redirecting path cannot leave the browser at that path. Measured: same step and destination content, a same-origin redirect passed 3 of 3 while a cross-origin one failed 3 of 3, so the trigger was the host changing rather than the redirect. Rather than a fourth prompt clause, `judge()` now receives the step's record of what was performed — a superset of the `lastResult` named above, since it carries every successful action of the step with its result — at both judge calls including the re-observation, and `navigate` reports where it landed when that differs from where it was asked to go. The cross-origin arm then passed 3 of 3, and the judge cited the redirect in its own reason, a fact present in no snapshot, which is what attributes the fix to the record rather than to the improved log line. The risk the lever carries is the mirror of what it fixes: the record could be read as evidence that a step's outcome holds, trading a wrong FAIL for the wrong PASS `judge-the-step` closed. It is stated to the judge that the record says what was *attempted* while the snapshot remains the only evidence of what is *true*, and checked against DEF-005's sibling reproduction from #28 — a successful click sitting in the record while the step's outcome is absent still fails, and still leaves nothing behind.
- Process note, 2026-07-31: this file said "deliberately NOT taken" for a full day after the lever had been taken, and an outside evaluation read it and reported the lever as still pending — twice, and in its conclusion. The evaluator was right about the file and wrong about the code, and the fault is the file's. Second instance in two days of documentation asserting something the code had since contradicted (the first was the derivation above `estimateMaxModelCalls`). A defect record is a claim about the present, not only a diary of the past: when the thing it says is deferred stops being deferred, the record is stale evidence.
